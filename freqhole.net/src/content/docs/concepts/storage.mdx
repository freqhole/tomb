freqhole reads your music + video collection. it never moves, renames, or deletes files you ask it to scan. here's where data lives depending on how you're running freqhole.

---

## the server (desktop app or CLI)

the server holds two things:

- **your media files** — wherever you already have them. freqhole scans directories you point it at. it reads files to extract metadata, artwork, and posters, then leaves them alone.
- **a metadata database** — a single SQLite file (by default `data/grimoire.db`) that stores music, video, artwork, posters, playlists, user accounts, and playback history. this is everything freqhole knows about your library.

freqhole does **not** copy, move, or rename scanned media files. if you delete a file from disk, freqhole will show it as missing — it won't clean it up on your behalf unless you explicitly run a maintenance command.

### where the database lives

| how you're running    | default location                                                      |
| --------------------- | --------------------------------------------------------------------- |
| desktop app (macOS)   | `~/Library/Application Support/net.freqhole.charnel/data/grimoire.db` |
| desktop app (Linux)   | `~/.local/share/freqhole/data/grimoire.db`                            |
| desktop app (Windows) | `%APPDATA%\net.freqhole.charnel\data\grimoire.db`                     |
| CLI                   | `./data/grimoire.db` (relative to config file, configurable)          |

the `data_dir` setting in `freqhole-config.toml` controls this:

```toml
data_dir = "/home/user/freqhole-data"
```

### artwork + posters

cover art extracted from music, art fetched from metadata providers, and video posters are stored as blobs managed by freqhole. thumbnails at multiple sizes are generated and stored alongside them.

---

### uploaded files

files uploaded via the web UI are saved to a date-based directory under `server.fetch_music.output_dir` (or `data/fetch/` if that config key isn't set):

```
{output_dir}/{YYYY}/{MM}/{blob_id}.{ext}
# e.g. /path/to/fetch/2026/03/a1b2c3d4.mp3
```

the filename is the internal blob ID — the original filename is stored in the database.

### yt-dlp fetched files

when fetching music by URL, each job gets its own subdirectory so partial downloads don't collide. the filenames come from the yt-dlp `--output` template in your config (default: `uploader-title-[id].mp3`):

```
{output_dir}/{job_id}/Artist-Title-[youtube-id].mp3
```

`output_dir` must be an **absolute path** in `freqhole-config.toml`:

```toml
[server.fetch_music]
output_dir = "/absolute/path/to/fetch"
```

### music synced from remotes

when you save music from a remote server (P2P or HTTP), it's organized into artist/album folders under `server.fetch_music.output_dir` (or `data/synced/` if not set):

```
{output_dir}/{artist}/{album}/{track}-{title}.{ext}
# e.g. data/synced/Mindless Self Indulgence/Frankenstein Girls Will Seem Strangely Sexy/01-Backmask.mp3

# multi-disc albums include the disc number:
# data/synced/Pink Floyd/The Wall/01-01-In the Flesh.mp3
```

special characters in artist, album, and title are stripped from directory and filenames. if a file already exists at that path, a numeric suffix is appended (`-1`, `-2`, etc.) — existing files are never overwritten.

## the web app

the web app stores everything locally in your browser. nothing is written to your file system.

### library metadata

when you connect to a server, the web app syncs music + video library indexes to **IndexedDB** — a structured database built into every modern browser. this is what lets you browse your library offline.

### media files

saved music + video is cached using the **Origin Private File System (OPFS)** — a private, sandboxed storage area that browsers provide to web apps. OPFS is not accessible to other sites or visible in your regular file manager.

cached media lets you keep playing when you're offline or have a slow connection. you can control how much is cached and clear it at any time from the app's settings.

### artwork + posters

album art, artist images, and video posters are stored in IndexedDB alongside library metadata.

### saving music from remotes

when you play or queue music from a remote server, the audio is saved to OPFS by default — so it's available offline the next time. a few specifics:

- **queue auto-save**: anything added to the queue from a remote is saved locally as it plays, ready for offline use.
- **P2P remotes**: music fetched over P2P is also saved locally by default.

both behaviors can be turned off in settings if you'd prefer not to keep local copies.

:::danger[purge]
to clear everything, use the app's settings or clear site data for `spume.freqhole.net` (or your self-hosted origin) in your browser's settings.
:::

## the desktop app (charnel)

charnel uses a local freqhole server embedded in the application. all storage follows the same rules as the CLI server above — the database and blob storage live on disk in the app's data directory, and your scanned media stays wherever you put it.

the app also has a local web view (similar to the web app), but because it talks to the local embedded server over a private channel, media and artwork are served directly — no OPFS caching needed.

### changing storage folders

in charnel's local wizard **settings**, these are separate operations:

- **select a new folder without moving** updates the data-directory setting,
  closes the app, and opens first-time setup for a fresh library/node next time.
  the old files are not moved or deleted.
- **select folder for future fetches** changes where subsequent music/video
  fetches are saved. existing files and their database paths stay where they are.
- **move existing files** preflights the destination, asks for typed
  confirmation, then runs before services start on the next launch.

:::caution[transport references are part of the move]
the `freqhole-blobz/blobs.db` transport index can retain absolute file
references separately from SQLite. storage moves register and verify the
copied files in that index before configuration cutover or source deletion.
if the index cannot be opened or repaired, the move stops with the source
files retained. do not delete the index to bypass an error.
:::

for eligible moves, destination files are never overwritten. identical media
can be reused after hashing; different media with matching names require an
explicit **merge**, which keeps both under distinct names and updates paths.
non-media/freqhole metadata in the destination blocks the operation. existing
destination media is not automatically imported: scan this folder afterward
using **library → add directory** if you want to add it.

keep both disks connected and stop all other freqhole apps, including older
versions and other nodes sharing that fetch folder. copies are verified before
database/config cutover, and old copies are deleted only after a durable
cutover. the original config remains at its existing path so launchers still
find it; host preferences, webview state, locks and empty folders can remain
there too. do not remove that original folder wholesale.

CLI equivalents (also available through charnel's terminal passthrough):

```sh
freqhole --config /path/freqhole-config.toml config storage preview move-data /new/folder
freqhole --config /path/freqhole-config.toml config storage queue move-data /new/folder --confirm "move my storage"
# close all other apps before applying:
freqhole --config /path/freqhole-config.toml config storage apply
```

use `move-fetch` or `select-data` instead of `move-data` for the other
restart-time operations; `--merge` explicitly permits renaming differing media
collisions. `config storage assign-fetch /new/folder` changes future fetches
only. folders must already exist and source/destination must not be nested.
symlinks and special files are rejected.

to verify known file-backed sources without changing the transport index:

```sh
freqhole --config /path/freqhole-config.toml config storage audit-references
# close all apps first; register verified sources without copying/deleting media:
freqhole --config /path/freqhole-config.toml config storage audit-references --repair
```

`--repair` verifies the bytes served by the transport store. unresolved files
are reported explicitly; reconnect a missing disk or correct its library
path rather than forcing repair. repair is repeatable and retains successful
registrations if interrupted. it does not scan arbitrary folders for moved
files or prune old redb references.

reference repair and blob cleanup solve different problems. `audit-references
--repair` re-registers known files only after verifying their hashes; it does
not remove stale external paths. the maintenance orphan-blob purge removes
unreferenced media-blob entries from active use and reclaims app-managed files
or stored blob data, while leaving scanned files outside the data directory alone. the
running P2P storage node also has automatic periodic iroh-blobs GC: once a
hash is no longer protected by blob metadata, GC can reclaim that whole hash.
it does not prune one stale path from a still-protected hash, and there is no
supported manual path-prune operation. do not edit or delete `freqhole-blobz/blobs.db`;
see the [maintenance guide](/guides/maintenance/) for safe cleanup steps.

for GUI app, use **library → audit and repair blob
references** in charnel's wizard. **audit only** hashes known source files;
**audit and repair** also registers verified paths with the running P2P
store. jobs continue after leaving the view; returning shows the latest
run, progress and unresolved-file errors.

rathole includes `maintenance_audit_blob_references` in its maintenance
command picker (repair defaults off), or use:

```text
/maintenance audit-references
/maintenance audit-references repair
```

these do not require closing the app.
the adjacent `freqhole-config.toml.storage-move.json` journal makes interrupted
moves resumable. fix the reported error and relaunch or run `config storage
apply`. `config storage cancel` is allowed only before copying starts. do not
delete a started journal, either folder, or the pre-change config backup to
try to force a restart.

## backing up

stop all freqhole apps before making a filesystem backup so SQLite/WAL and the
blob stores are consistent. preserve the config and the whole configured data
folder, including `grimoire.db`, `haruspex.db`, `reliquary.db`, `blob-files/`,
`freqhole-blobz/`, identity files, and any legacy blob-data database still
present. include separately configured database/fetch folders and your original
media too.

`freqhole-blobz/blobs.db` is an upstream redb transport index, not another SQLite
database. some entries reference external files by absolute path; moving a
backup to a different root therefore also needs reference relocation, not just
a `data_dir` config change.
